We've All Done This

The "final_final_v2.doc" Problem

Almost everyone has a folder that looks like this at some point:

📄 report.doc
📄 report_final.doc
📄 report_final_v2.doc
📄 report_final_v2_REALLY_FINAL.doc
📄 report_final_v2_REALLY_FINAL_use_this_one.doc
💡
Real-World Application

Ask the room: "Who has a folder that looks exactly like this right now?" — almost everyone will relate. This lived frustration is exactly the problem Git was built to solve, permanently. No idea what changed, no safe way to undo, and total chaos the moment more than one person touches the same file.

Concept · Step 01

What Git Actually Is

Git is a version control system — software that tracks every change made to your files over time, letting you save checkpoints and return to any of them later. A repository (repo) is simply a folder that Git is "watching." Git runs entirely locally on your machine by default.

📁

A plain folder — nothing tracked

→
📁👁️

Git is now watching this folder

💡
Real-World Application

Think of Git as an extremely detailed, automatic "track changes" for your entire project folder — not just one document, but every file, every folder, all tracked together as one coherent history.

Concept · Step 02

git init — Starting A Repository

git init — run once, inside a folder, to turn it into a Git repository. This creates a hidden .git folder — where Git quietly stores the entire history of the project.

terminal
$ cd course-project
$ git init
Initialized empty Git repository in /home/aditi/course-project/.git/
💡
Real-World Application

This is the very first command run in almost every real coding project — before writing a single line of code, professionals initialize a Git repo so that from commit #1, every future change is tracked.

Concept · Step 03

The Save-Point Game Analogy

Think of your project like a video game — and Git as the save system. git add chooses what goes into the save; git commit actually saves it, with a note describing what happened.

Concept · Step 04

git add — The Staging Area

git add filename tells Git "include this specific change in my next save." git add . stages everything changed at once. This two-step process (add, then commit) lets you choose exactly what goes into each save-point.

terminal
$ echo "Hello Git" > notes.txt
$ git add notes.txt
# notes.txt is now staged, ready to commit
💡
Real-World Application

In real projects, developers often change multiple files at once but only want to commit the ones related to a specific fix — git add lets you group related changes into one clean, meaningful commit, instead of one messy commit with everything mixed in.

Concept · Step 05

git commit — Saving A Checkpoint

git commit -m "message" permanently saves the staged changes as a new checkpoint. The message should describe what changed and why. Each commit gets a unique ID and joins the project's permanent history.

5 commits, repeated cycle
$ git add notes.txt
$ git commit -m "Add initial notes"
[main a1b2c3d] Add initial notes
$ echo "more text" >> notes.txt
$ git add notes.txt
$ git commit -m "Add more detail to notes"
[main d4e5f6g] Add more detail to notes
... repeated for 5 total commits
💡
Real-World Application

This add → edit → commit cycle repeats dozens of times a day for a working developer — small, frequent, well-described commits make a project's history genuinely useful later, instead of one giant unexplained dump of changes.

Concept · Step 06

git log — Viewing Your Save History

git log shows the complete history of every commit made in this repo, most recent first. Each entry shows: a unique commit ID, the author, the date, and your message.

terminal
$ git log --oneline
d4e5f6g Add more detail to notes
a1b2c3d Add initial notes
💡
Real-World Application

When debugging a problem that "used to work," professionals use git log to find exactly when and in which commit something broke — turning "it's broken somehow" into "it broke specifically here."

Concept · Step 07

Local Repo vs Remote Repo (GitHub)

Everything so far happens only on your own machine — your local repo. GitHub hosts a copy of your repo online — a remote repo. Local and remote stay in sync through two actions: push and pull.

Step by Step

Creating A GitHub Repo & Pushing

Five steps to move your local history online, matching the live-demo flow.

01

Create a free GitHub account (if not already done) and log in

02

Click "New repository", give it a name, and create it — leave it empty, no README yet

03

Link your local repo to the new remote: git remote add origin <url>

04

Push your existing commits up: git push -u origin main

terminal
$ git remote add origin https://github.com/username/course-project.git
$ git push -u origin main
Branch 'main' set up to track 'origin/main'.
💡
Real-World Application

This exact flow — local commits, then pushed to GitHub — is how virtually every collaborative software project works, including massive open-source projects with thousands of contributors, and how you'll submit your own capstone project later in this course.

Concept · Step 08 · The Key Visual

Branches — A Parallel Save-Line

A branch is a separate, parallel line of history — you can change things without touching main at all. The default branch is usually called main — your stable, official version.

💡
Real-World Application

Teams use branches constantly so multiple people can work on different features at the same time, without one person's unfinished, possibly-broken work affecting anyone else's — this is the single biggest reason Git enables real team collaboration.

Step by Step

Creating & Using A Branch

Extending the game analogy: a branch is a parallel save-file — jump into it, try something bold, and if it goes badly, your original save (main) is completely untouched.

terminal
$ git branch new-feature
$ git checkout new-feature
Switched to branch 'new-feature'
$ echo "experimental change" >> notes.txt
$ git add notes.txt
$ git commit -m "Try a new idea"
$ git checkout main
Switched to branch 'main'
$ cat notes.txt
(experimental change is not here)
💡
Real-World Application

This exact "branch, experiment, switch back" pattern is how real teams safely try new features without ever risking the stable, working version of a product that real users depend on.
